# P0-009 — Establish initial benchmark corpus

## Status

REVIEW after application; DONE only after complete-checkout reproduction and independent review.

## Objective

Create the first versioned, deterministic benchmark corpus covering coding, analysis, path safety, crash recovery, browser capability honesty, and research/citation tasks.

## Dependencies

- `P0-001`

## In scope

- Versioned suite and fixtures.
- Dependency-free benchmark runner.
- Explicit pass/fail/unavailable/unsupported/not-run/error semantics.
- Portable committed baseline and human-readable report.
- Optional model-candidate and machine/SDK execution paths.
- Unit, repository, reproducibility, verification, CI, schema, and source-manifest integration.
- P0-007 assurance boundaries when that milestone is present.
- P0-008 roadmap-control integration when that milestone is present.

## Out of scope

- Claiming production benchmark thresholds.
- Calling source checks behavioral proof.
- Installing or selecting a model provider.
- Live web or browser automation.
- Hiding failed or unsupported cases.
- Replacing the complete P8 evaluation hierarchy.

## Required implementation

1. Define six benchmark categories with at least two cases each.
2. Add local coding, analysis, browser, and research fixtures.
3. Execute stable offline gates where current behavior is available.
4. Record SDK-dependent cases as unavailable in portable mode.
5. Record absent browser capability as unsupported.
6. Record model-dependent cases as not-run until a candidate is supplied.
7. Commit a byte-reproducible portable JSON and Markdown baseline.
8. Add candidate materialization/evaluation support.
9. Add JSON schemas, unit tests, repository integration tests, CI and verification hooks.
10. Preserve all earlier milestone security and governance behavior.

## Required tests

- Duplicate and malformed suite cases fail.
- Unsafe command execution is rejected.
- Two portable runs are byte-equivalent.
- Baseline drift is detected.
- Failed, unavailable, unsupported, and not-run states remain visible.
- Source-only analysis never becomes behavioral proof.
- A valid coding candidate can pass its immutable acceptance test.
- A candidate cannot replace the authoritative acceptance test.
- Valid analysis and research candidates can pass structured evaluation.
- A browser candidate cannot override a missing browser capability.
- Browser source/tool signals without behavioral evidence remain unsupported.
- Unknown or forward case dependencies are rejected.
- The result fingerprint detects report mutation.
- Output redaction removes roots and common credentials.

## Acceptance criteria

- [ ] Six required categories exist and each has at least two cases.
- [ ] Portable baseline is byte-reproducible from one checkout.
- [ ] Baseline contains no network, credentials, dynamic timestamp, or model-provider dependency.
- [ ] Browser absence is `unsupported`, never fabricated success.
- [ ] Model tasks are `not_run` without a candidate.
- [ ] Current failed cases remain recorded.
- [ ] Unit and repository gates pass.
- [ ] Source manifest contains the suite, evaluator, schemas, fixtures, and baseline.
- [ ] Independent reviewer confirms the claim boundaries.
