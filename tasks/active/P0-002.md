# P0-002 — Disable insecure v1 trust decisions

Status: **REVIEW**
Roadmap phase: **P0 — Stabilize, contain, and establish truth**
Depends on: **P0-001**
Product behavior changed: **yes — legacy v1 trust operations now fail closed**

## Objective

Remove the self-authenticating v1 trust path before adding Owner Mode, browser automation, external agents, plugins, or managed updates. The retired protocol placed the HMAC secret in `signer.publicKey` inside the untrusted envelope and verified with that same attacker-controlled value. It could prove internal consistency but not signer identity.

## Security invariant

No v1 envelope handled by `tool/interoperability_v19.py` may generate credentials, create a trust envelope, or return a successful verification result. The only permitted behavior is a stable `v1_trust_disabled` rejection that points to Signed Manifest v2.

## Acceptance criteria

1. `LEGACY_TRUST_ENABLED` is permanently `False` in the v1 helper.
2. Key generation, signing, and verification all raise `InteroperabilityError` with code `v1_trust_disabled`.
3. Rejection occurs before reading `signer.publicKey`, algorithm, payload hash, or signature bytes.
4. The exact attacker construction—choose secret, sign arbitrary manifest, put secret in `signer.publicKey`—is rejected.
5. Mapping and typed `SignedManifestEnvelope` inputs have identical fail-closed behavior.
6. Malformed and algorithm-substituted envelopes cannot bypass disablement.
7. The helper contains no HMAC comparison or success-return path.
8. The executable gate is invoked by `tool/verify.sh` and `tool/validate_release.py`.
9. Source-contract validation requires the disablement markers and attacker regression.
10. Legacy types remain readable for migration and diagnostics, but cannot establish authority.

## Implementation

- Replaced the active trust behavior in `tool/interoperability_v19.py` with a single fail-closed policy.
- Retained legacy dataclasses, canonical JSON, hashing, and old signing-material serialization solely for migration/diagnostic compatibility.
- Added `legacy_trust_status()` as a stable machine-readable receipt.
- Added dependency-free `tool/v1_trust_disablement_test.py` with eight behavioral and source-hardening cases.
- Added the gate to `tool/verify.sh` before dependency resolution.
- Added a dedicated executable release-validation check to `tool/validate_release.py`.
- Added source-contract assertions to `tool/system_test.py`.
- Updated roadmap status and source-manifest hashes.

## Deliberately not changed

- `tool/release_ops_v19.py` and `tool/interoperability_admin_v19.py` retain their separately implemented external-key lookup behavior for compatibility until the canonical v2 migration. They do not use the envelope-supplied-key verifier disabled here.
- Signed Manifest v2, Ed25519, RFC 8785 canonicalization, external keyrings, revocation, and TUF are P1 work.
- CI formatting and downstream platform failures are P0-003.
- Security-policy and public documentation rewrites are P0-005.

## Reproduction

```bash
python3 tool/v1_trust_disablement_test.py \
  --json-output release/V1_TRUST_DISABLEMENT_RESULTS.json

python3 -m py_compile \
  tool/interoperability_v19.py \
  tool/v1_trust_disablement_test.py \
  tool/system_test.py \
  tool/validate_release.py

python3 tool/system_test.py --project .
python3 tool/validate_release.py --skip-sdk --skip-tests
```

The first command must report exactly `8/8` passing cases and:

```json
{
  "enabled": false,
  "errorCode": "v1_trust_disabled",
  "replacement": "signed_manifest_v2"
}
```

## Completion rule

Move this task to **DONE** only when:

- the patch is applied to the complete repository;
- the source manifest verifies with no missing or modified entries;
- the eight-case gate passes from that checkout;
- source validation passes;
- an independent reviewer confirms that no success path remains in the retired helper; and
- the evidence receipt is committed.
