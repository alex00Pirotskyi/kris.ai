## Why another handoff is required

The protected `main` workflow contains the reviewed dependent `pr14-repair` job. However, GitHub evaluates pull-request workflow structure from the pull-request workflow context. PR #48 deliberately points at a fixed, stale trigger commit, so its workflow definition contained only the three product matrix jobs and did not schedule the newly added dependent repair job.

Changing the trigger head merely to import the controller would invalidate the exact successful run and exact-head authorization. Pinning the replacement head inside the same replacement commit would also create a circular hash dependency.

The safe resolution is a separate workflow that is reviewed through a normal protected pull request and executes only after its own merge to protected `main` on a `push` event.

## Challenges passed

### Pull-request workflow definition mismatch

The successful PR #48 matrix did not schedule the protected-base dependent job because the fixed trigger commit did not contain that newer workflow structure. The solution does not reinterpret the green run as proof that an absent job ran; it uses the run only as immutable product evidence and performs candidate construction from protected-main code.

### Circular trigger-SHA authorization

Embedding the expected trigger SHA in code committed to that same trigger branch is self-referential. The handoff keeps the trigger immutable and moves executable authorization into independently protected `main`.

### Workflow-file write restrictions

GitHub correctly prevents an ordinary Actions token from updating a branch when the candidate changes `.github/workflows/ci.yml` without workflow-write authority. The helper treats only the known workflow-write rejection as an acceptable non-push outcome, records the exact candidate object and complete receipt, and permits a separately authenticated connected ref update only after that receipt is verified.

### Evidence and branch clutter

Historical one-shot recovery refs were removed before this step. The new handoff does not depend on any deleted branch and includes a permanent progress record, so completion can retire its own temporary branch without losing the reasoning or evidence chain.

### Claim discipline

The source product run, candidate validation, workflow-write receipt, protected reconciliation, final landing, owner-risk evidence closure, independent security review, public-GA eligibility, and production-release eligibility remain distinct claims. None is inferred from another.
