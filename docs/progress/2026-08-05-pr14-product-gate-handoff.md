## Why the handoff moved into product-gates

Multiple reviewed event-transport mechanisms remained fail-closed but did not produce an observable `repair-status.json` receipt:

1. A direct Actions push constructed a valid child commit, but GitHub correctly refused to update a workflow file without workflow-write authority.
2. Connector-authored commits did not reliably emit the expected push-triggered workflow.
3. A same-repository pull-request helper ran ordinary checks but did not publish the specialized receipt.
4. An exact-SHA `pull_request_target` helper was reviewed, merged, and restricted to non-PR code, but reopening the trigger PR still produced no receipt.
5. A broad `workflow_run` handoff was reviewed and merged, but one later Ubuntu hosted runner stalled inside package installation. Windows and macOS completed successfully; the incomplete run was rejected.
6. A run-and-attempt-pinned `workflow_run` helper verified two successful attempts of run `30950745333`, but no receipt was emitted.
7. An explicit owner-only issue comment was posted with exact owner, `OWNER` association, target SHA, nonce, and comment ID. No receipt was emitted.

No missing receipt was classified as success. No two-platform result was promoted. No roadmap, source-inventory, trust, or security gate was bypassed.

`product-gates` differs from those transports in one important way: it is already the protected required workflow that GitHub has repeatedly executed and exposed for every recovery-control PR. The new handoff is therefore not a separate listener. It is a dependent job in the same run and uses the matrix result as a hard prerequisite.

## Workflow-write rejection and receipt semantics

The helper attempts to push the exact candidate to the target branch. Only two outcomes are accepted:

1. the exact ref update succeeds and is verified through `git ls-remote`; or
2. GitHub returns the known workflow-write permission rejection, after the candidate object has been transferred and remains available for a separately authenticated connected ref update.

Every other push failure is rejected.

The status branch receives a schema `1.4.0` receipt containing:

- target branch and exact expected head;
- trigger branch, SHA, and PR number;
- current product run ID and attempt;
- candidate commit SHA;
- whether the Actions token moved the target ref;
- executor run ID and attempt;
- `docs/roadmap/MASTER.md` as roadmap authority;
- exact authorized target paths;
- focused repair result code.

Publishing the receipt changes the disposable trigger branch away from its pinned SHA. The same PR state can therefore not schedule another repair job, providing one-shot behavior without hidden mutable state.
