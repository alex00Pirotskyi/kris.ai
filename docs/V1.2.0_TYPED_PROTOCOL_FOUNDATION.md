# Kristin v1.2.0+120 — Typed protocol and tool-schema foundation

## Purpose

V1.2.0 is the first V2 foundation release. It replaces coordinator-local, prose-driven action contracts with versioned typed decisions and one canonical generated tool registry while preserving the v1 execution coordinator through an explicit compatibility bridge.

The release is intentionally focused. It does not introduce SQLite durability, crash recovery, OS sandbox workers, network/secret brokers, or a new Project Manager UI. Those remain dependent releases.

## Canonical decision protocol

`schemas/agent_decision.v1.json` defines protocol version `1.0.0` and exactly five decision kinds:

| Decision | Required payload | Current v1 bridge |
|---|---|---|
| `tool` | `tool`, `arguments` | Executed after schema and policy validation |
| `complete` | `summary` | Converted to the legacy completion action |
| `fail` | `summary` or `reason` | Converted to the legacy failure action |
| `ask_user` | `question` | Typed and validated; rejected by the v1 coordinator bridge until the durable kernel supports waiting states |
| `delegate` | `delegateTo`, `task` | Typed and validated; rejected by the v1 coordinator bridge until governed delegation exists |

The Dart implementation is in `lib/product/agent_decision.dart`. Provider-specific envelopes are translated in `lib/product/agent_protocol.dart`; the workflow coordinator no longer owns the adapter class.

## Provider adapter boundary

The same canonical decision is produced from:

- Ollama JSON or text responses;
- OpenAI-compatible function/tool-call envelopes;
- MCP tool-call envelopes;
- recorded diagnostic/replay envelopes.

Canonical non-tool decisions are decoded before the legacy bridge. In particular, failure `code`, `retryable`, `summary`, and `reason` survive direct and provider-wrapped envelopes instead of being flattened into a generic legacy failure. Legacy `answer`/`final` completion carriers still fall back through the bounded compatibility parser.

Compatibility normalization is bounded and auditable. Declared aliases may be promoted to canonical fields. Conflicting canonical and alias values fail. Unknown authority-bearing fields, including working-directory overrides not declared by a tool schema, fail rather than being guessed.

## Canonical tool registry

`schemas/tool_registry.v2.json` is the source of truth for all 23 governed tools. Every tool declares:

- name and semantic contract version;
- permission scope and risk class;
- data boundary and idempotency class;
- strict input JSON Schema;
- strict output JSON Schema;
- legacy compatibility aliases;
- safe defaults;
- canonical example used for model repair.

`tool/generate_protocol_contracts.py` validates the registry and deterministically generates `lib/product/generated/protocol_contracts.g.dart`. The generated source carries the registry, AgentDecision schema, tool-name inventory, schema versions, and a full contract digest.

Regenerate or verify with:

```bash
python tool/generate_protocol_contracts.py
python tool/generate_protocol_contracts.py --check
```

## Dispatch order

Every governed call now follows this boundary:

```text
provider envelope
  → provider adapter
  → typed AgentDecision
  → declared alias/default canonicalization
  → input-schema validation
  → compatibility audit
  → permission authorization
  → project-boundary path normalization
  → final input-schema validation
  → input hash audit
  → tool handler
  → output-schema validation
  → output hash/evidence audit
```

Missing `write_file.content`, conflicting aliases, wrong JSON types, invalid values, and undeclared arguments therefore cannot reach a side-effecting handler.

Output validation is deliberately after the handler because it validates the actual result envelope. A schema-invalid result is classified as a non-retryable deterministic tool/runtime defect and is not accepted as completion evidence.

## Retryability taxonomy

Protocol and tool-schema errors carry one typed classification:

- `never` — deterministic runtime, policy, or unsupported bridge state;
- `model_correction` — the model may repair its decision without changing authority;
- `state_refresh` — a new bounded observation is required;
- `transient` — infrastructure may be retried under an explicit budget.

This is a foundation for the v1.3 durable workflow retry taxonomy; it does not yet replace all legacy coordinator error paths.

## Compatibility policy

V1.2.0 retains the proven v1.1.7 replay behavior and supports bounded legacy carriers such as nested `action`, `tool_call`, `function.arguments`, `action_input`, `filePath`, and direct command vectors. Compatibility is allowed only when it preserves meaning and does not invent authority.

Examples:

- `filePath` to `path`: allowed when no conflicting canonical `path` exists;
- nested `action.content` to canonical `arguments.content`: allowed;
- command vector to `executable` plus `args`: allowed for the declared command tool;
- missing `content`: rejected;
- external working-directory override: rejected;
- conflicting alias and canonical values: rejected.

## Validation and replay gates

The source release includes:

- Dart behavioral contracts in `test/product/typed_protocol_schema_test.dart`;
- a dependency-free Python gate in `tool/protocol_contract_test.py`;
- 2,000 deterministic provider-envelope fuzz cases;
- missing-mutation-data fuzzing proving malformed writes cannot dispatch;
- exact registry/handler coverage checks for all 23 governed tools;
- representative runtime result envelopes validated against all 23 output schemas;
- a negative mutation-result case proving incomplete output evidence is rejected;
- canonical failure-metadata preservation across direct and recorded envelopes;
- the two v1.1.7 production diagnostic replays as permanent gates;
- generator-current checks in CI, quick test, release validation, and platform verification scripts.

Primary source-only commands:

```bash

python tool/system_test.py --project .

```

## Architectural result

The coordinator remains large, but two important responsibilities have moved behind stable boundaries:

1. provider envelope parsing and decision typing;
2. tool contract declaration, canonicalization, validation, repair examples, and provider descriptors.

The legacy `AgentAction` remains only as a bridge for the current coordinator. New protocol work should target `AgentDecision` and generated tool contracts, not add envelope branches back into `RunCoordinator`.

## Known limits

- Mutable product state is still atomic JSON rather than SQLite event history.
- Runs are not yet crash-resumable or idempotent across process failure.
- Agent-controlled commands and MCP servers are not yet OS-sandboxed.
- `ask_user` and `delegate` are schema-valid but deliberately unsupported by the legacy coordinator bridge.
- The lightweight Dart schema validator implements the subset used by Kristin's governed schemas; the generator and Python gate reject unsupported registry structures.
- Native Dart formatting, Flutter analysis, Flutter tests, and platform builds remain authoritative when SDKs are available.

## Next release

V1.3.0 should introduce the durable workflow kernel and SQLite migration: append-only events, transactional materialized state, checkpoints, idempotency keys, crash replay, retry taxonomy integration, and compensation records. The typed decision and tool contracts in this release are the required input boundary for that work.
