# Kristin v1.5.0+150 — Prompt Studio 2 and deterministic plan compiler

## Purpose

V1.5.0 introduces a deterministic compilation boundary between model-authored product intent and governed execution. The model may propose a product specification, prompt, evaluation dataset, or task graph. Kristin does not treat those documents as executable authority. It validates them against versioned contracts, derives capabilities, checks policy and evidence coverage, computes a stable execution schedule, and produces an inspectable compilation report before any side effect is possible.

This release is intentionally based on the durable v1.3.0 workflow kernel. It does **not** claim that the v1.4.0 operating-system sandbox milestone has been completed. Process-, network-, MCP-, deployment-, and other sandbox-dependent tasks fail compilation unless sandbox availability is explicitly declared. A separately named legacy unsandboxed override exists only for reviewed local dry-run compatibility; it is warned, approval-bearing, and never silently enabled.

## Canonical contracts

Prompt Studio 2 adds five reviewed JSON contracts:

```text
schemas/product_specification.v2.json
schemas/task_plan.v2.json
schemas/prompt_evaluation_dataset.v1.json
schemas/plan_capability_catalog.v1.json
schemas/plan_compilation_report.v1.json
```

The contracts describe:

- structured product intent, users, requirements, exclusions, assumptions, platforms, data policy, artifacts, acceptance criteria, tests, deployment boundary, and risk;
- hierarchical plans containing 1–100 tasks with stable IDs, parents, dependencies, capabilities, tools, artifacts, evidence, verification, budgets, retry/stop policy, and manual status;
- prompt evaluation cases with variables, required and forbidden terms, criterion terms, expected mode, weights, and tags;
- the mapping from task types and validators to the 23 governed tool contracts;
- deterministic compilation output, issues, task state, quality, dry-run simulation, input hash, and output hash.

Unknown fields are rejected at authority-bearing boundaries. IDs, counts, paths, enums, array uniqueness, ranges, and graph references are validated before compilation.

## Deterministic compiler

`tool/plan_compiler.py` and `lib/product/prompt_studio_v2.dart` implement the same compilation policy. The compiler:

1. validates the specification, plan, policy, and capability catalog;
2. verifies stable IDs and references;
3. detects dependency and parent-hierarchy cycles;
4. infers required capabilities from task type, proposed tools, artifact operations, and validators;
5. requires every inferred capability to be declared by the task;
6. maps capabilities only to governed tools;
7. rejects unknown tools and tools outside a task's capability envelope;
8. checks local-only, network, secret, deployment, human-workflow, and self-modification policy;
9. enforces the missing-v1.4 sandbox prerequisite;
10. checks required artifact producers and deterministic validators;
11. links acceptance criteria to resolvable evidence;
12. rejects conflicting producers without an ordering dependency;
13. preflights aggregate model/tool/repair/effort budgets;
14. computes a stable topological order and execution batches;
15. emits a side-effect-free simulation and quality report;
16. hashes canonical input and output so identical inputs produce identical results.

A compilation report is executable only when it contains no blocking issue. Warnings and required approvals remain visible and auditable.

## Capability and policy boundary

The v1 capability catalog currently defines 11 capabilities over the existing 23 governed tools:

```text
project.inspect
project.mutate
project.verify
process.execute
process.manage
git.inspect
knowledge.retrieve
research.network
deployment.package
external.mcp
human.approval
```

Capabilities do not grant permission. They prove only that a plan is internally coherent and can be mapped to known tools. Actual execution still requires the existing project, run, task, tool, path, network, and approval controls.

Because v1.4 is not implemented, capabilities that require an OS worker are blocked by default. The compiler records `sandbox_required` rather than allowing the model to assume isolation exists.

## Structured product specification

`ProductSpecificationV2` makes the result of idea refinement inspectable and versionable. Required sections include:

- problem statement and target users;
- functional and non-functional requirements;
- excluded scope, assumptions, and clarification questions;
- target platforms;
- local/cloud data policy and sensitivity;
- required artifacts and their validators;
- acceptance criteria linked to validator IDs;
- test strategy;
- deployment boundary and required approval;
- risk classification.

A required artifact must declare at least one validator. An acceptance criterion must identify evidence that the compiler can resolve to a declared validator.

## Hierarchical 1–100 task plans

`TaskPlanV2` supports 1–100 tasks. A task can refer to a parent for hierarchy and separate dependencies for execution order. Parent hierarchy does not imply execution dependency; both graphs are checked independently.

Each task declares or carries:

- objective, type, mode, enabled/manual status;
- parent and dependency IDs;
- input and output artifacts;
- required capabilities and proposed governed tools;
- acceptance criteria and verification declarations;
- complexity, risk, uncertainty, and confidence;
- effort and model/tool/repair budgets;
- retry and stop policy.

The compiler derives the ready/blocked state of each task, allowed tools, approvals, topological index, and execution batch. It never executes the graph during compilation.

## Dry-run simulation

Compilation always includes a simulation summary:

```text
dryRun: true
sideEffectsPerformed: false
```

The simulation reports task counts, ready/blocked/manual/disabled totals, batch count, critical-path effort, material output paths, aggregate budgets, local-only state, sandbox state, and required approvals.

Dry run is a plan proof, not a claim that every task will succeed against a real project. Native tool execution, artifact validation, and environment health remain separate runtime facts.

## Prompt and plan evaluation

Prompt Studio 2 includes deterministic preflight evaluation against a versioned user-authored dataset. It measures whether a prompt version contains the declared variables, terms, constraints, criterion language, mode cues, and forbidden-content protections. It returns per-case results, weighted score, schema validity, and a stable hash.

Plan revision comparison compiles both revisions under the same specification and policy, then reports changes in:

- executability;
- error and warning count;
- quality score and grade;
- task count and schedule;
- input/output hashes.

These graders measure contract and policy quality. They are not a semantic guarantee of model reasoning or produced-artifact quality.

## Relationship to the durable v1.3 kernel

V1.5 compilation is deliberately side-effect free. Once a report is executable and approved, the existing v1.3 kernel remains responsible for durable runs, append-only events, leases, idempotency records, checkpoints, compensation records, file-mutation recovery, and uncertainty handling.

The compiler does not bypass:

- typed `AgentDecision` validation;
- tool input/output schemas;
- project boundary checks;
- permissions and approvals;
- SQLite operation identity;
- evidence validation;
- cancellation and retry taxonomy.

This separation prevents another monolithic planner/coordinator branch.

## Honest limits

- V1.4 OS sandboxing, network brokering, secret brokering, and platform workers are not implemented or claimed.
- Existing process execution still has the desktop user's privileges. Sandbox-dependent v2 plans therefore fail closed unless a human explicitly selects the legacy dry-run override.
- The full visual Prompt Studio 2 editor, diff experience, dataset editor, and simulation UI are not yet complete; runtime, API, CLI, schemas, and compiler are implemented.
- The release fixtures compile and simulate 161 tasks; they do not execute 161 real project mutations.
- Static prompt evaluation measures declared deterministic features, not end-to-end semantic success.
- Native Dart/Flutter compilation and platform integration remain authoritative when SDKs are available.
- Real plan execution remains subject to project state, model behavior, environment availability, permissions, and objective artifact verification.
