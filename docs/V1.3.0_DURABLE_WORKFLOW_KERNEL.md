# Kristin v1.3.0+130 — Durable workflow kernel and SQLite

## Release purpose

V1.3.0 makes mutable application state and run execution durable before increasing autonomy. It preserves the v1.2 typed `AgentDecision` and tool-schema boundary, then places a transactional SQLite authority underneath repositories, run state, tool idempotency, checkpoints, task attempts, compensation, and recovery.

The release target is not uninterrupted execution under every possible machine failure. The target is precise restart semantics: after a process exits, Kristin can distinguish an operation that never committed, one whose material effect was recorded, one whose result was durably acknowledged, and a workspace that was committed before the final run snapshot.

## Storage authority

The application data root now contains:

```text
state/workflow.sqlite3                 authoritative mutable state
state/workflow.sqlite3-wal             SQLite write-ahead log while active
state/workflow.sqlite3-shm             SQLite shared-memory file while active
support/migration-backups/             byte-exact database and legacy JSON backups
logs/events.jsonl                      best-effort compatibility mirror
checkpoints/<run-id>/                  file mutation rollback material
research-archive/...                   content-addressed immutable objects
cache/...                              disposable derived indexes
```

Whole-collection JSON files are accepted as legacy import sources, not as the runtime authority. Existing research objects and derived indexes remain outside SQLite because they have different immutability and lifecycle requirements.

SQLite is configured with foreign keys enabled, WAL journaling, `synchronous=FULL`, a bounded busy timeout, and immediate write transactions. The current generated schema version is **4**.

## Transactional run history

`DurableWorkflowStore.saveRun` updates the materialized `runs` row and appends a `run.snapshot` event in one `BEGIN IMMEDIATE` transaction. Each event carries a canonical payload hash and monotonically increasing state version. SQLite triggers make `run_events` append-only.

The current run projection can be rebuilt from the event history. Integrity verification checks:

- SQLite integrity and foreign keys;
- run snapshot hashes;
- event payload hashes;
- materialized projection versus the latest durable run snapshot;
- generated schema version and migration digest.

## Side-effect idempotency

Every governed tool operation derives an idempotency key from:

```text
run ID
+ work-item ID
+ attempt number
+ logical operation
+ SHA-256 of canonical normalized arguments
```

An idempotency record moves through `in_progress`, `completed`, or `failed`. A completed record stores the canonical result and result hash. Replaying the same operation returns the prior result rather than invoking the handler again. Reusing a key with different normalized arguments fails as `idempotency_key_collision`.

Expired operations may be reclaimed only according to operation class. Non-compensatable operations such as arbitrary commands, managed-process starts, deployment packaging, and MCP calls are not silently repeated after ambiguous failure.

## File mutation compensation

A workspace mutation is journaled before the filesystem effect:

```text
prepared → applied → committed
                   ↘ rolled_back | rollback_failed
```

The record includes operation, canonical relative path, prior existence, before/after hashes, backup path, work item, and idempotency key. Startup reconciliation compares the journal with current filesystem hashes:

- no effect observed: operation may be retried;
- exact recorded effect observed: result may be recovered without repeating the write;
- pre-effect state observed: rollback/retry remains possible;
- ambiguous state: stop with `transaction_recovery_required`.

A committed change set receives a durable `workspace_committed` checkpoint. Rollback outcomes are also checkpointed.

## Run leases, checkpoints, and recovery

A running coordinator owns a short durable run lease and renews it during persisted state changes. Another process cannot execute the same live run. When a lease expires, startup reconciliation evaluates durable checkpoints and run items:

- committed workspace plus all items succeeded: recover the run as `succeeded`;
- otherwise: recover it as `interrupted` with an explicit reason;
- never infer success from model prose alone.

Task attempts, operation claims, material mutations, verification, approval boundaries, and terminal outcomes can be checkpointed independently.

## Retry taxonomy

`WorkflowRetryTaxonomy` separates transient infrastructure, protocol repair, tool input, state conflict, verification, unavailable resource, policy rejection, deterministic bug, and lease loss. Policy/security rejection is not automatically retried. Lease loss fails closed. A failed transient idempotent operation may release its lease for a bounded retry; a completed result remains immutable.

## Legacy JSON migration

At first startup, v1 JSON collections and documents are imported with these guarantees:

1. source bytes are hashed;
2. a byte-exact backup is written and verified;
3. records are inserted transactionally with existing SQLite values preserved;
4. a `migration_imports` ledger records source hash, path hash, backup, count, and details;
5. repeated startup with the same source hash is a no-op.

Before any schema migration or legacy import against an existing database, Kristin takes a consistent pre-startup database backup after a full WAL checkpoint. Any later startup failure—including a corrupt legacy file after earlier imports—restores that backup. A failed first startup removes the partially created database, WAL, and shared-memory files.

Legacy files are not deleted automatically. Keep them until the new database has passed integrity verification and an external backup has been made.

## CLI and diagnostics

New source-only commands include:

```bash
python tool/generate_workflow_migrations.py --check
python tool/workflow_kernel_test.py --project .
./kristin test --workflow-kernel --project .
./kristin workflow --data-root <data-root> --json
./kristin workflow --data-root <data-root> --run-id <run-id> --json
```

Diagnostic export reads SQLite as the authority and includes bounded, redacted workflow summaries, run events, checkpoints, task attempts, idempotency records, compensation state, recovery decisions, and migration-import records. It falls back to legacy JSON only when no workflow database exists.

## Executable release gate

`tool/workflow_kernel_test.py` executes 14 network-free cases with Python’s SQLite binding and the exact reviewed SQL migrations:

- generated registry freshness;
- WAL/FULL schema configuration;
- append-only event guards;
- forced process exit inside an uncommitted transition;
- forced exit after a completed idempotent effect and result;
- completed-result immutability and required-result guards;
- prepared/applied compensation recovery;
- checkpoint-based committed-run recovery;
- projection rebuild from event history;
- concurrent writers without lost updates;
- pre-migration backup and restore;
- legacy JSON backup and import ledger;
- startup rollback integration contracts;
- Dart runtime integration contracts.

The v1.1.7 production replays and v1.2 protocol/schema fuzzing remain blocking gates.

## Scope intentionally deferred

V1.3.0 does not claim:

- OS-isolated command, MCP, or file-adapter workers;
- network or secret brokers;
- distributed/multi-device SQLite replication;
- executable durable `ask_user` or delegated-agent waiting states;
- automatic compensation for non-compensatable external effects;
- native desktop validation in an environment without Dart/Flutter.

Those boundaries belong to v1.4.0 and later. V1.3.0 is a durable-kernel source release, not a sandbox release.
