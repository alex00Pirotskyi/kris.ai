# Kristin Local Agent v1.0.5+105 path and validation hygiene hotfix

This source release repairs two failures reported from a configured Windows Flutter workstation.

## 1. Bounded recovery for model-generated absolute paths

The active project remains Kristin's only filesystem authority. A model may nevertheless emit a path copied from another machine, a stale checkout, or a generic agent container such as `/workspace/project`.

Before dispatching a filesystem tool, the coordinator now attempts a deterministic, bounded normalization:

- Absolute paths already inside the active project keep their existing safe normalization.
- A stale absolute path containing the active project's directory name can be anchored to that project.
- Common virtual roots such as `/workspace`, `/project`, `/repo`, and their Windows equivalents can be converted to a project-relative suffix.
- Root-scoped read operations such as directory listing and text search can fall back to the selected project root.
- Existing read targets may use an unambiguous suffix that already exists inside the selected project.

Every recovered candidate is resolved again through `WorkspaceBoundary`. Symlink escapes, parent traversal, URI schemes, hidden paths, secret-like paths, and paths outside the selected project remain rejected.

Mutation recovery is intentionally narrower. A write, replace, patch, or delete can be rebased only when the path identifies the active project by name or uses a recognized virtual workspace alias. Kristin does not infer an arbitrary external destination. To modify another folder, register and select that folder as the active project first.

Successful recovery emits:

```text
tool.path_rebased_to_active_project
```

The event records the original path only as a SHA-256 hash, the normalized relative path, the strategy used, and `securityBoundaryPreserved: true`.

An unsafe or ambiguous external path still emits:

```text
tool.path_recovery_rejected
```

and remains blocked. After the bounded in-attempt correction attempts are exhausted, a genuine outside-project path is not retried as a fresh work-item attempt; the user receives a direct project-scope failure instead of spending the complete run repair budget on the same invalid destination.

## 2. Generated Flutter and native files are not source-release inputs

A normal Flutter Windows build creates files such as:

```text
windows/flutter/ephemeral/flutter_windows.dll
windows/flutter/ephemeral/flutter_windows.dll.pdb
```

Those binaries are generated workstation state. They are not source files and should not cause source validation to fail merely because they exceed the source-size limit.

V1.0.5 introduces one shared policy in `tool/source_tree_policy.py`. The same policy is used by:

- governed source validation;
- secret scanning; and
- deterministic release packaging.

It excludes known generated Flutter/native directories and common build caches, including `windows/flutter/ephemeral`, while still rejecting oversized files or symlinks elsewhere in the source tree. Generated files are neither trusted nor packaged; they are ignored as reproducible build output.

## Verification

On a configured Windows workstation, run:

```powershell
dart format .
dart format --output=none --set-exit-if-changed .
flutter pub get
flutter analyze
flutter test
.\kristin.cmd test --system --project .
.\kristin.cmd test --release --project .
flutter run -d windows
```

`test --system` and `test --release` may be run after a Windows build has populated `windows/flutter/ephemeral`; those generated files should no longer produce a release-tree hygiene failure.

## Security boundary

This hotfix improves compatibility without allowing arbitrary cross-project access. The selected project remains the sole filesystem scope. Path recovery never grants a tool, permission, network capability, secret, or process capability that the current work item did not already possess.
