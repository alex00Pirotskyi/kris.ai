# Kristin Local Agent v1.0.0+100 product preview

Kristin v1.0 introduces a governed **Prompt → Plan → Execute → Verify** workflow while preserving the chat-first workspace, project boundary, permissions, transactions, evidence, research archive, memory, logs, and audit trail from v0.9.

This package is a complete source release. It is not a signed installer or a claim that every production-hardening item is complete.

## Reported absolute-path failure

Previous builds rejected every absolute tool path with:

```text
path_absolute_rejected: Tool paths must be relative to the active project.
```

That was secure but unnecessarily brittle. Local models often repeat the absolute project folder shown in context, even when the path points to the already approved project.

v1.0 applies this rule:

1. `.` and ordinary project-relative paths continue to work.
2. An absolute path that resolves inside the canonical active project is converted to a project-relative path before the tool runs.
3. A local `file:` URI is accepted only when it resolves inside the active project.
4. Parent traversal, non-file URI schemes, NUL bytes, symlink escapes, and absolute paths outside the selected project remain blocked.
5. Normalization is audited with the original path represented only by SHA-256 and the normalized project-relative path recorded for debugging.
6. A recoverable path or argument mistake is returned to the model for up to three bounded correction attempts instead of immediately terminating the work item.

This does not broaden project access. The canonical project boundary is still enforced again when an existing file, missing-file parent, or symbolic link is resolved.

## AI Prompt Composer

Prompt Studio starts with a plain-language goal, for example:

```text
Build me a modern calculator application with standard and scientific functions.
```

The selected model returns a structured, editable draft containing:

- title and purpose;
- durable system instructions;
- user prompt template;
- variables and assumptions;
- material clarifying questions;
- measurable acceptance criteria;
- expected outputs;
- guardrails and stop conditions;
- evaluation cases;
- recommended task mode.

The model response is schema-validated. Invalid responses receive bounded repair prompts. Actions include **Generate**, **Improve**, **Simplify**, and **Add detail**. A generated draft is never silently accepted or executed.

Every saved change creates an immutable `PromptVersionRecord` containing its source goal, generation action, model identity, content hash, creator, and timestamp. Re-saving identical content reuses the current version instead of creating meaningless duplicates.

## Adaptive 1–100 task plans

An approved prompt version can be converted into an adaptive task plan. The task limit is a ceiling, not a target:

- atomic requests can remain one task;
- small work can use a few tasks;
- larger projects can use phases and dozens of tasks;
- exhaustive plans are capped at 100 executable tasks.

Each task retains:

- phase and optional parent;
- objective and bounded instructions;
- dependency IDs;
- acceptance criteria and verification steps;
- expected artifacts;
- proposed governed tools;
- complexity from 1–10;
- effort points;
- uncertainty and risk;
- estimate confidence;
- expected model turns and tool calls;
- retry limit;
- enabled and manual flags.

The model may propose tools but cannot authorize them. Unknown tools are removed and required permissions are derived from the governed registry during compilation.

Plan validation rejects missing dependencies, duplicate IDs, self-dependencies, dependency cycles, enabled tasks that depend on disabled tasks, empty non-manual acceptance criteria, and plans over the configured task limit.

## Immutable plan editing

Editing a generated task creates a new `TaskPlanRecord`:

```text
revision = previous revision + 1
previousPlanId = prior plan ID
new plan ID and content hash
```

The prior plan remains available for comparison, recovery, and audit. Running or approved plans are never overwritten in place.

## Selective execution and stop controls

Prompt Studio supports:

- **Run all tasks**;
- **Review execution plan** before approval;
- run one selected task with all transitive prerequisites;
- edit one task and save a new plan revision;
- stop active generated-plan runs through the existing safe cancellation path.

The deterministic compiler converts the selected plan revision into the existing governed runtime:

```text
PromptVersionRecord + TaskPlanRecord
              ↓
validated selected dependency graph
              ↓
TaskContract revision 3 + ExecutionPlan
              ↓
permission review
              ↓
RunCoordinator and governed tools
```

A selected task never runs without its required dependencies. Manual tasks must be completed or disabled before compilation. The existing coordinator owns pause, resume, cancellation, managed-process stopping, evidence, mutation checkpoints, rollback, and terminal run memory.

## API

The authenticated loopback API includes:

```text
GET  /v1/prompts
POST /v1/prompts/generate
POST /v1/prompts/versions
GET  /v1/prompts/{promptId}/versions

POST /v1/task-plans/generate
GET  /v1/task-plans
GET  /v1/task-plans/{planId}
PUT  /v1/task-plans/{planId}
POST /v1/task-plans/{planId}/compile
```

Plan `PUT` creates a new immutable revision. Compile can run the full enabled plan or a selected task set plus dependencies. Existing token scopes and project-bound authentication remain enforced.

## System-test CLI

The complete test ladder is:

```text
kristin test --quick   # offline source, grammar, architecture, and secret checks
kristin test --full    # quick + format check + pub get + analyze + Flutter tests
kristin test --system  # full + v1 Prompt-to-Task and recovery fixtures
kristin test --release # system + release validation + two identical ZIP builds
```

On PowerShell, use the current-directory prefix:

```powershell
.\kristin.cmd test --system --project .
.\kristin.cmd test --release --project .
```

Each invocation writes JSON, Markdown, and raw log reports under `reports/` unless a JSON output path is supplied.

The system command runs deterministic offline contract fixtures on every machine. When Flutter is installed it also runs the behavioral test suite, including:

- in-project absolute-path normalization;
- continued blocking of outside and traversal paths;
- prompt generation and immutable versions;
- task generation, editing, and compilation;
- selected-task dependency expansion;
- valid 100-task plans and cycle rejection.

## Data additions

v1.0 adds two local state collections:

```text
state/prompt_versions.json
state/task_plans.json
```

Existing v0.9 prompts, projects, research records, knowledge, and memory remain compatible. Generated prompt and task-plan records are local project/product metadata; they do not grant permissions or modify source by themselves.

## Production boundary

The following roadmap items remain outside this source preview:

- OS-enforced isolation for agent processes, interpreters, MCP servers, and file workers;
- migration from JSON collections to transactional SQLite;
- fully crash-safe mutation journaling across every operating-system failure window;
- connection-time DNS pinning for research requests;
- signed installers, notarization, and authenticated updates;
- dedicated validated producers for every document, media, CAD, and specialist format;
- externally anchored audit integrity.

Use trusted projects, review requested permissions, inspect generated plans, and review support or knowledge exports before sharing them.
