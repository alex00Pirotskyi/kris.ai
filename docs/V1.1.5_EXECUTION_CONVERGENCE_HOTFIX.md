# Kristin Local Agent v1.1.5+115 execution-reliability redesign

## Diagnostic reviewed

This release is based on the complete saved diagnostic archive for run:

```text
run_hklfhuqkrwdoQ11swy34hvARke
```

The run used Kristin v1.1.4+114 with Ollama `phi4-mini:latest` against the selected project `test6`. The request described an interactive calculator-style web application with mouse and keyboard input, immediate results, and session calculation history.

The terminal error was:

```text
work_item_failed: argument_required: Argument "executable" is required.
```

That message was only the final link in a longer convergence failure.

## Causal chain

1. Prompt Studio generated a six-task plan that was much broader than the requested static calculator. It included system-tool installation, a sibling `MathWebApp` directory, an Express REST backend, MCP access, public-deployment preparation, and a general-purpose process tool.
2. The first task correctly targeted `docs/design/wireframes.md`, but its instructions omitted the approved calculator requirements.
3. The selected model created an unrelated e-commerce wireframe containing product listing, product detail, shopping-cart, and checkout flows.
4. The coordinator accepted the file as mutation progress because it checked that a file changed, but not that the artifact matched the requested product.
5. The model submitted the same file contents three more times. Every identical rewrite was journaled, backed up, and counted as a new mutation even though the before and after SHA-256 values were identical.
6. The model then repeated inspections. Loop recovery stopped the first attempt, but the retry prompt did not carry the useful evidence from attempt one.
7. On attempt two, the model returned a nested command array:

```json
{
  "action": {
    "type": "run_command",
    "command": ["git", "-C", "/MathWebApp/project-directory", "status"]
  }
}
```

8. The protocol adapter recognized `run_command` but discarded the nested `command` array, so the tool received no `executable`.
9. `argument_required` was not classified as a repairable tool-input error. The work item therefore failed immediately despite substantial remaining run budget.

The diagnostic also showed that model-loading recovery, failed-memory isolation, project registration, and the global run budget were functioning. They were not causal in this failure.

## Corrections

### Nested command compatibility

The domain parser and protocol adapter preserve command arrays found at top level or inside `action`, `tool`, `function_call`, `tool_call`, and OpenAI-style tool-call envelopes.

A generic vector becomes:

```json
{
  "tool": "run_command",
  "arguments": {
    "executable": "node",
    "args": ["tool/check.js", "--json"]
  }
}
```

A model-generated Git status or diff command is specialized to the existing project-scoped `git_status` or `git_diff` tool when that tool is already allowlisted. Model-supplied repository-root overrides are ignored rather than executed.

Missing required command arguments and rejected process-scope paths are repairable for at most the existing bounded tool-repair allowance.

### Process argument boundary

Finite and managed process arguments are checked for absolute paths. Paths inside the selected project are normalized to project-relative arguments. External paths, `file:` paths outside the project, Git `-C`, `--git-dir`, and `--work-tree` overrides are rejected with hashed provenance.

Windows-style slash options such as `/q` remain options rather than being misclassified as Unix absolute paths.

### No-op mutations

A write whose bytes already match the file now returns:

```text
operation: noop
mutated: false
```

No backup is created, no transaction-journal record is appended, and no mutation budget is charged. The audit chain and run event stream record the no-op with the before and after hashes.

Repeated no-op writes are redirected to one artifact inspection instead of creating backup churn or pretending that progress occurred.

### Product-specific artifact validation

The bounded artifact policy applies only to artifact-producing wireframe/design and usability-checklist tasks. It does not force mutation during a read-only design review.

For calculator wireframes, deterministic completion requires:

- a named project-relative artifact;
- material mutation evidence for that path;
- inspection of the final artifact;
- calculator or arithmetic scope;
- the four basic operations;
- keyboard interaction;
- session calculation history;
- immediate result feedback;
- user flows, responsive states, interaction states, and accessibility notes;
- absence of unrelated commerce or checkout flows.

A write result alone is never enough to finish these bounded artifact tasks. If the model tries to complete without inspecting the required artifact, Kristin emits `work_item.artifact_evidence_required` and requests the missing inspection. After the bounded correction limit, it fails with `artifact_evidence_missing` rather than accepting an unverified file.

An incomplete artifact receives at most two targeted corrections. A complete inspected artifact can finish the bounded design task without waiting for another slow model turn. An unrelated artifact stops with `artifact_scope_mismatch` rather than being accepted as product progress.

### Retry continuity

A later attempt receives a bounded, redacted history of the previous attempt's retained evidence. Material mutation paths are reconstructed without counting historical no-op records. This prevents the retry from starting as if the artifact had never been created or inspected.

### Prompt Studio capability alignment

Generated plans now carry a bounded approved-product context into design, setup, usability, and implementation tasks.

- Design tasks are least-privilege and cannot request `run_command`, arbitrary binary writes, Git, or MCP merely to write a Markdown wireframe.
- Environment-setup tasks initialize the selected project root. They do not install Node.js, npm, Git, SDKs, or create a sibling project directory.
- A server or Express task is replaced with a client-side calculation engine and session history when the approved product does not require a server, API, database, authentication, shared persistence, or cloud synchronization.
- The rewrite requires an explicit backend implementation verb, so testing or verification tasks that merely mention backend references remain testing or verification tasks.
- Local-only deployment remains a local preview, governed package, and manual hosting guide without claiming a public URL.

### Diagnostic clarity

Model progress events now distinguish:

```text
workItemAttempt
modelLoadAttempt
modelLoadMaxAttempts
```

Tool-repair events distinguish the work-item attempt from the tool-repair count. Saved diagnostics include an **Artifact scope and convergence** section, and no-op mutation events are available in the run timeline.

## Regression coverage

The release adds behavioral fixtures for:

- the exact nested `git -C /MathWebApp/project-directory status` response;
- generic nested command arrays;
- tool allowlist preservation;
- unrelated e-commerce wireframes;
- valid calculator wireframes;
- material mutation requirements;
- read-only design reviews;
- identical writes with no journal or backup;
- repeated no-op write recovery;
- setup-task and unnecessary-backend normalization;
- preservation of testing tasks that mention backend references without requesting backend implementation;
- product-context propagation and least-privilege design tools;
- structured release lineage and diagnostic provenance.
